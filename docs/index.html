SpriteForge

Pixel sprites, colour variants, timeline clips and state-machine behaviours for games that cannot load image files. Every sprite becomes a small set of coloured rectangles drawn by one runtime file; the bundled runtime targets Lua client scripts, and the data format works with any engine that can draw a rectangle. The editor runs in 15 languages (auto-detected from the browser, switchable in the top bar). Open the editor · Source code on GitHub (open source, MIT).

Why this exists

Some game editors do not let creators upload images. Everything on screen is built from the built-in asset list. A plain square image, tinted and resized many times, is the only way to show something the platform has never seen - a mascot, a dish, a crop, a card frame. Doing that by hand is tedious and expensive: every rectangle is a UI control. SpriteForge turns pixel art into the fewest rectangles it can, keeps the result editable, and adds the things a sprite needs to live inside a game: recolourable palettes, layers, frame animation, procedural clips and a state machine the game drives with events.

Editor setup (once per stage)

The easiest way is one file, spriteforge.lua. It holds your sprites, the runtime that draws them and a start script, so you download and attach only this file. Programmers who want to control sprites from their own scripts can use separate files instead (see Separate files below).

One file: step by step

  1. Open your stage in the editor and save it once, so its folder exists.
  2. UI Control Group Library → Client Control Templates → new template of type Image: name T_PIXEL, image 100001 (white square), size 10×10, pivot and anchor centred, Initially Visible on. Write down its Control Template Index ID.
  3. In SpriteForge open Export, type that number into Image template Index, choose what to show when the game starts (sprite, size, X, Y) and press Download spriteforge.lua.
  4. Find the folder: Client Script Resource Explorer → right-click → New Client Script. A file window opens in the external_lua_file folder of this stage; copy its path from the address bar. The empty script it made can be deleted.
  5. Copy spriteforge.lua into that folder. If an older copy is there, replace it.
  6. Client Script Resource Explorer → right-click → Batch Add Script Files → Add by Folder. Check that spriteforge now appears in the list. A file without a mapping never reaches the game.
  7. Manage UI Control Groups → Interface Layout → Add UI Control → Client Control Container, name it PX_Root and stretch it to full screen. (0, 0) is the centre of the screen.
  8. On PX_Root: Script tab → Add Script → spriteforge.lua. No script variables are needed.
  9. Ctrl+S, restart the Sandbox completely, Test Play. Logs → Client Scripts should show SpriteForge: 1 sprite(s) ready.

Clickable sprites: make a CursorEventArea template (10×10, centred), type its index into Export → Tap template Index and download again. Sprites with a behaviour then receive the tap event.

The top of spriteforge.lua holds the settings from Export, so small changes can also be made right there:

local TEMPLATE = 1073741900      -- Image template Index (nil = read the TPL_SPRITE script variable)

Several sprites in one stage

Tick all of them in Export so they go into one pixdata.lua (the game reads one per stage), then create each one in init() of the main script:

local hero, coin

local function init()
  local root = Px.root(script, "TPL_SPRITE")
  if not root then return false end
  hero = Px.spawn(root, "potion", -200, 0, { px = 6 })
  coin = Px.spawn(root, "coin", 200, 0, { px = 4 })
  return hero ~= nil
end

Clickable sprites (optional)

  1. Make a second template of type CursorEventArea, 10×10, centred, and write down its index.
  2. Add a second script variable TPL_HIT, type Client Control ID, value = that index.
  3. In the script: hero:onTap(function(actor) actor:fire("tap") end). Without TPL_HIT, Px.hit() and onTap() simply return nil.

Updating

After redrawing: export pixdata.lua again, replace the file, Ctrl+S and restart the Sandbox. When SpriteForge itself updates, replace pix.lua as well. Mappings, the main script and editor settings stay.

Workflow

  1. Draw or import. Import a picture as pixel art (downscaled, quantised to N colours, optional outline) or as a drawing (overlapping triangles, ellipses or rectangles), a sprite sheet (cells become frames), ASCII rows with a legend, or a previously exported pixdata.lua. Or draw from scratch with pencil, fill, line, rectangle, mirror-X and layers.
  2. Palette. Keys named p0…p3 and q0…q3 are tint slots. Define override palettes (blue, red, gold…) that only replace those keys; one sprite then has as many variants as you have palettes, at no extra cost.
  3. Layers. Mark a layer S (separate) to export it as its own sprite name/layer. The runtime can show and hide it per state (hat on, hat off) or you can draw it alone.
  4. Animate. A clip is a timeline with tracks on x y sx sy rot alpha frame pal layer:<name>. Loop clips (idle, float) run forever; one-shot clips (squash, celebrate, fadeout) fire an end event. Presets give you idle/bounce/squash/shake/float/fadeout/frames in one click.
  5. Behave. States choose a clip, a palette and layer visibility; transitions fire on game events (tap), on timers (random 3-6 s), when a clip ends, or when a parameter crosses a threshold (energy < 0.3). The preview panel lets you fire events and drag parameters.
  6. Export. spriteforge.lua is one file with everything the game needs: sprites, palettes, clips, behaviours, the runtime and a start script. Programmers can take pixdata.lua and pix.lua separately instead. Save the .spriteforge.json project next to your Lua sources to keep editing later.

Drawing sprites (vector)

Besides pixel art, a sprite can be a drawing: brush strokes, lines, circles and boxes (New sprite… → Drawing). It works with everything else: palettes and variants, layers and parts, frames, clips, behaviours, tweens and particles.

The editor stores shapes; for the game each shape is compiled into primitives that use three built-in assets: 100001 (square), 100002 (circle) and 100003 (triangle). A stroke becomes one rotated rectangle per segment plus circles at its ends and corners; a filled rectangle is one square, a filled ellipse one stretched circle, a filled triangle one stretched triangle (tip at the middle of the top edge, base along the bottom edge), all turned when the shape is turned. The editor preview draws exactly these primitives, so the game shows the same picture. Translucent colours show slightly darker where pieces of one stroke overlap, in the editor and in the game alike.

D.V["smile"] = { w = 64, h = 64, ax = 32, ay = 64, n = 13, k = { "out", "skin" },
  p = { 2, 32, 32, 52, 52, 0, 1,   -- asset (1 square, 2 circle, 3 triangle), x, y, w, h, rotation, colour index
        2, 32, 32, 46, 46, 0, 2, ... } }

Units are drawing units with y going down, like the pixel grid; px (default D.PX) gives screen units per drawing unit. Rotation is clockwise on screen; the runtime converts it for the UI. Cost = number of primitives; the Smoothing slider of the brush lowers it.

From a picture

Import image… → Drawing turns a picture into overlapping filled triangles, ellipses or rectangles (choose one kind or a mix; triangles and ellipses is the default), each with its own position, size, angle and one of N colours (up to 64). Every step tries many random shapes, improves the best ones by small changes and keeps the shape that brings the drawing closest to the picture. Transparent parts of the picture stay empty. Each shape is one primitive, so the number of shapes is the cost: 80-150 are enough for an icon, 300 or more come close to a detailed picture. With soft blending on, a shape may also be half transparent when that brings the drawing closer: it mixes with the shapes below, which gives smooth shading for the same cost. Half transparent shapes only lie over parts that are already covered, so the outline stays solid. If the fit ends before the number of shapes you asked for, more shapes would not bring it closer; add colours or turn on soft blending. The result is a normal drawing sprite 64 units wide that you can recolour, edit, animate and export.

Examples

Every example uses the sample potion sprite. In the editor, Guide → "Add this example to my project" adds it with all its colours, clips and behaviour, and the Guide shows each example running live.

Show a sprite

local Px = require("pix")
local root = Px.root(script, "TPL_SPRITE")
local a = Px.spawn(root, "potion", 0, 0, { px = 6 })   -- (0, 0) = centre of the container
-- every frame: Px.update(dt)

A static picture that never animates is cheaper to manage with Px.draw:

local icon = Px.draw(root, "heart", -300, 200, { px = 4 })
icon:pos(-280, 200)   icon:scale(1.5, 1.5)   icon:alpha(0.5)   icon:destroy()

Colour variants

The potion's liquid uses the tint slots p0…p3. The variants blue, green and gold only redefine those four keys.

Px.spawn(root, "potion", -150, 0)                      -- base (red)
Px.spawn(root, "potion",  -50, 0, { pal = "blue" })
Px.spawn(root, "potion",   50, 0, { pal = "green" })
local p = Px.spawn(root, "potion", 150, 0, { pal = "gold" })
p:tint("blue")                                          -- change later

Parts

The label is drawn on its own layer marked part, so the game can hide it:

a:layer("label", false)   -- hide
a:layer("label", true)    -- show

Frames and clips

Frames are drawings (a flip-book). Clips are movement over time and can switch frames with a frame track. The potion has three clips:

ClipTracksLoop
idleframe 1 → 2 (step), y 0 → 2 → 0 (inOutQuad), 1.2 syes
popsx 1.3 → 1, sy 0.6 → 1 (outBack), pal gold → base, 0.5 sno, fires end
drainalpha 1 → 0, y 0 → -8 (outQuad), 0.8 sno

Ready-made presets: idle, bounce, squash, shake, float, spin, fadeout, frames. How a clip looks in pixdata.lua:

D.C["potion.idle"] = { dur = 1.2, loop = true, tracks = {
  { prop = "frame", ease = "step",      keys = { {0, 1}, {0.6, 2} } },
  { prop = "y",     ease = "inOutQuad", keys = { {0, 0}, {0.6, 2}, {1.2, 0} } } } }
a:play("idle")                         -- or "potion.idle"
a:on("clipEnd", function(actor, clip) print(clip .. " finished") end)

Making one in the editor: Animate → + Preset… (or + Clip) → choose what should change and press + Track → click the track where a key should be and type its value → Space plays.

Lua API (pix.lua)

local root = Px.root(script)                -- container object; also reads TPL_SPRITE

n:tint("red")  n:alpha(0.5)  n:flip(true)  n:repaint("crate#2")

-- actors: sprite + clips + behaviour
local a = Px.spawn(root, "potion", x, y, { pal = "blue", px = 4, behavior = "potion" })

local walls = Px.tiles(root, "wall", grid, 64)                 -- autotiles: grid[y][x] = true
local hit = Px.hit(root, x, y, w, h, function() end)           -- needs TPL_HIT
a:onTap(function(actor) actor:fire("tap") end)

-- every frame
function OnUpdate(dt) Px.update(dt) end

Px.count       -- live rectangle controls created by SpriteForge
Px.get(name)   -- decoded sprite { w, h, ax, ay, rects }
Px.color(key, palName)

Coordinates: pos is in UI units relative to the parent, y up. Clip x/y are in sprite pixels and are multiplied by px, so a clip looks the same at any size. Rotation is counter-clockwise degrees. Frames of one sprite reuse the same controls: switching frames creates no new controls.

More runtime features

All of these are driven by Px.update(dt).

CallWhat it does
a:on("event", fn(actor, name))Clip events: an ev track in a clip holds named keys; they are sent at that moment of the clip (loops included). Use for sounds, hit frames, footsteps.
a:playOnce(clip, done)Plays a clip once, then returns to the clip that was playing; done(actor) is called at the end. Does not send end to the behaviour.
a:speed(m)Clip playback speed multiplier (1 = normal).
a:flip(on), a:face(dx)Mirror the sprite; face flips by the sign of a movement.
n:moveTo(x, y, dur, ease, done)
n:moveBy(dx, dy, …), n:scaleTo(s, …), n:rotTo(deg, …), n:fadeTo(a, …)		Tweens on any node or actor, in UI units, added on top of clips. Returns a handle for Px.cancel. fadeTo repaints in 5 % steps.
Px.tween(node, {x=, y=, sx=, sy=, rot=, alpha=}, dur, ease, done)The general form of the tweens above.

Data format (pixdata.lua)

TableContent
D.P[palette][key] = {r,g,b,a}Palettes. base must contain every key; other palettes override a subset.
D.S[name] = {w,h,ax,ay,n,k,r}Rect mesh. k is the key order, r packs 5 chars per rectangle (x, y, w, h, key index) using printable ASCII 35-126 without backslash, so each value is 0-90. Sprites wider or taller than 91 pixels (up to 256×256) use the wide form z=2: x, y, w and h take two characters each (hi × 91 + lo), 9 characters per rectangle. Frame 2+ is name#2; a separate layer is name/layer (with the same frame suffix).
D.A[name]Sprite meta: w, h, frames, fps, layer names, separate layers, lod, tiles, nine = {l,t,r,b}.
name@2, name~tl…Half-resolution LOD copy (drawn at 2×px), and the nine 9-slice pieces. Autotile sprites carry 16 frames in the order none, n, e, ne, s, ns, se, nse, w, nw, we, new, sw, nsw, sew, nsew (bit 1 = N, 2 = E, 4 = S, 8 = W).
D.C["sprite.clip"]{ dur, loop, tracks = { { prop, ease, keys = { {t, v}, … } } } }. Numeric props interpolate with the track ease; frame, pal and layer:* step; ev keys are event names sent when playback passes them.
D.B[name]{ initial, params, states = { name = { clip, pal, layers, on = { {ev=…}|{timer={a,b}}|{param=…, lt|gt=…}, to=… } } } }

The encoder paints larger colour regions first and lets later colours overlap them, which is why the 12×16 sample potion costs 34 rectangles instead of 150. Translucent keys (alpha < 255) are never painted under other colours. The format is stable across versions: files exported by older SpriteForge builds keep working with newer pix.lua.

Rectangle budget

Each rectangle is one UI control. From shipped games on the platform: keep live SpriteForge rectangles under roughly 2 000 on PC and 1 200 on phones for a steady 60 fps. The editor shows the cost of every sprite and of the whole project; the runtime exposes Px.count. Ways to spend less: fewer colours (the Simplify button merges rare colours), flat fills instead of noise, outlines only where they read, px for size instead of resolution, the half-res LOD for small copies, and destroying sprites that leave the screen.

FAQ

Can sprites be clicked? Add your own hit control (a template with a raycast target) on top; SpriteForge rectangles have no raycast target so they never block taps.

Can I use this outside the UI (3D world)? No - Lua client scripts in 7.1 control UI only, so SpriteForge is for HUDs, cards, menus and games that live entirely in UI.

Does it change my save or stage files? No. It only produces Lua tables; nothing touches .gia/.gil.

Which languages? English, 简体中文, 繁體中文, 日本語, 한국어, Español, Français, Русский, ไทย, Tiếng Việt, Deutsch, Bahasa Indonesia, Português, Türkçe, Italiano. The editor picks the browser language and remembers the one you choose.

Where is my project stored? In the browser (localStorage) while you work; use Save to download the .spriteforge.json file and keep it in your repository.
